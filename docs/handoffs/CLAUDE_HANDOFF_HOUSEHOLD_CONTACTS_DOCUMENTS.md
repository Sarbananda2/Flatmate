## 1. Domain Context & Core Purpose

Following the physical Room Inventory (Migration 0010), we are completing the Household Property model by adding:
1. **Property Stakeholders & Contacts:**
   - **Property Owner (Landlord):** Name, Phone, Email, PAN (for HRA tax proof), Bank Account / UPI ID.
   - **Broker:** Name, Agency, Phone, Brokerage Fee (paise), Payment Status (`paid`, `pending`).
   - **Caretaker / Society Manager:** Name, Phone, Role/Responsibilities (Plumbing, Electrical, Gate Passes, NOC).
   - **One-click Contact Shortcuts:** Direct Call (`tel:`), WhatsApp (`wa.me`), and Mail (`mailto:`) shortcuts matching our tested design pattern.
2. **Household Document Vault:**
   - Secure, self-contained binary storage in PostgreSQL (`BYTEA`) with cryptographic SHA-256 verification.
   - Categories: `lease_agreement`, `society_noc`, `police_verification`, `inventory_handover`, `other`.
   - Operations: Upload (multipart), preview, download, and delete.

---

## 2. Invariants & Security Rules

* **Invariant H1 (Self-Contained Database Backups):** Documents are stored in `BYTEA` inside the database. When `./scripts/manage.py backup` is executed, the `.dump` file restores both the financial ledger and every legal contract.
* **Invariant H2 (Cryptographic Integrity):** Every document is hashed with SHA-256 on intake. The hash is asserted and written to `audit_log` on upload and deletion.
* **Invariant H3 (Metadata Separation):** `GET /api/property/documents` returns document metadata **excluding** the heavy `BYTEA` payload so the document directory loads instantly. Files are streamed only on `GET /api/property/documents/{id}/download`.
* **Invariant H4 (Design System Adherence):**
  - All table headers must be center-aligned (`text-center`).
  - All form fields (contacts and document uploads) must enforce client-side validation.

## 3. Database Schema Migration (`0011_household_contacts_and_documents.sql`)

Create migration `aem/persistence/postgres/migrations/0011_household_contacts_and_documents.sql`:

```sql
-- Migration 0011: Household Contacts, Stakeholders, and Document Vault

-- 1. Household Contacts (Owner, Broker, Caretaker, Society)
CREATE TABLE household_contact (
    contact_id TEXT PRIMARY KEY,
    apartment_id TEXT NOT NULL REFERENCES apartment(apartment_id) DEFERRABLE,
    role TEXT NOT NULL CHECK (role IN ('owner', 'broker', 'caretaker', 'society_manager', 'emergency_utility')),
    name TEXT NOT NULL CHECK (length(trim(name)) > 0),
    phone TEXT,
    email TEXT,
    
    -- Owner / Landlord specific details (used for HRA & payouts)
    pan TEXT,
    bank_account_no TEXT,
    bank_ifsc TEXT,
    upi_id TEXT,
    
    -- Broker specific details
    agency_name TEXT,
    fee_amount_paise BIGINT CHECK (fee_amount_paise IS NULL OR fee_amount_paise >= 0),
    fee_status TEXT CHECK (fee_status IS NULL OR fee_status IN ('paid', 'pending', 'na')),
    
    -- Caretaker / Emergency specific details
    responsibilities TEXT,
    
    notes TEXT,
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL,
    row_seq BIGINT GENERATED BY DEFAULT AS IDENTITY
);

CREATE INDEX idx_household_contact_apartment ON household_contact(apartment_id);
CREATE INDEX idx_household_contact_role ON household_contact(role);

-- 2. Household Document Vault
CREATE TABLE household_document (
    doc_id TEXT PRIMARY KEY,
    apartment_id TEXT NOT NULL REFERENCES apartment(apartment_id) DEFERRABLE,
    title TEXT NOT NULL CHECK (length(trim(title)) > 0),
    category TEXT NOT NULL
        CHECK (category IN ('lease_agreement', 'society_noc', 'police_verification', 'inventory_handover', 'other')),
    filename TEXT NOT NULL,
    content_type TEXT NOT NULL,
    size_bytes BIGINT NOT NULL CHECK (size_bytes > 0),
    sha256 TEXT NOT NULL CHECK (length(sha256) = 64),
    content BYTEA NOT NULL,
    uploaded_by_resident_id TEXT REFERENCES resident(resident_id) DEFERRABLE,
    notes TEXT,
    uploaded_at TEXT NOT NULL,
    row_seq BIGINT GENERATED BY DEFAULT AS IDENTITY
);

CREATE INDEX idx_household_document_apartment ON household_document(apartment_id);
CREATE INDEX idx_household_document_category ON household_document(category);
```

## 4. Backend Implementation

### 4.1 Schemas (`aem/schemas/models.py`)
- `ContactCreate` & `ContactUpdate`:
  - `role`: Literal['owner', 'broker', 'caretaker', 'society_manager', 'emergency_utility']
  - `name`: str (min 1, max 200)
  - `phone`, `email`, `notes`
  - `pan`, `bank_account_no`, `bank_ifsc`, `upi_id`
  - `agency_name`, `fee_amount_paise`, `fee_status`
  - `responsibilities`
- `ContactResponse`: Full model with formatted fee.
- `DocumentMetadataResponse`:
  - `doc_id`, `apartment_id`, `title`, `category`, `filename`, `content_type`, `size_bytes`, `sha256`, `uploaded_at`, `uploaded_by_resident_id`, `notes`.
  *(Does not include `content` bytes)*.

### 4.2 Repositories & Services (`aem/persistence/repositories/property.py` & `aem/services/property.py`)
- Contacts: `list_contacts`, `create_contact`, `update_contact`, `delete_contact`.
- Documents:
  - `list_documents(uow, apartment_id)`: returns metadata only.
  - `upload_document(uow, apartment_id, file, title, category, notes, actor)`: calculates SHA-256 and saves bytes.
  - `get_document_content(uow, doc_id)`: returns file stream, filename, content_type.
  - `delete_document(uow, doc_id)`.
  - All mutations logged to `uow.audit`.

### 4.3 Routers (`aem/api/routers/property.py`)
- `GET /api/property/contacts`
- `POST /api/property/contacts`
- `PATCH /api/property/contacts/{contact_id}`
- `DELETE /api/property/contacts/{contact_id}`
- `GET /api/property/documents` (metadata list)
- `POST /api/property/documents` (multipart upload)
- `GET /api/property/documents/{doc_id}/download` (file download)
- `DELETE /api/property/documents/{doc_id}`
